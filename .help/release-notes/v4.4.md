# TiXL v4.4 - Release Notes (WIP)

## Support for Mac, Linux and Windows

With v4.4 a dream comes true. We have been working towards this step for several years, but with the new Vulkan abstraction layer these efforts finally show a remarkable result: TiXL is truly cross-platform. With very few exceptions, all projects, operators and examples work on all platforms. All project file formats are compatible and you can freely jump between them.

## Rendering on Vulkan

You don't need to understand the technical background to create projects with TiXL and can skip this section.

### Why we can't rely on Windows

On Windows, TiXL was using the Windows graphics API DirectX to render with your graphics card. For reasons that only Microsoft's management knows, it never created an API to access DirectX from C#, so the ecosystem had to rely on SharpDX - an open source project by [Alexandre Mutel](https://github.com/xoofx) - until he retired the project a couple of years ago. At the same time, Microsoft tried to compete with Metal and Vulkan and created a completely new version 12 of DirectX -- again without any support for C#. To make things worse, newer versions of DX11 were limited to Windows 11.

Additionally, driven by recent decisions from Microsoft and the increasing instability and slowness of the platform, we have seen a significant movement of creatives and developers towards alternative platforms. The only way forward was to use a new graphics API: Vulkan.

Just like DX12, Vulkan is extremely awkward to work with: It's verbose, low-level and finicky. But there is excellent cross-platform support. And there are a few things that made porting TiXL easier than we expected:
- 95% of all user interface code is using ImGui and C#. So the UI runs out of the box on all platforms (this was the primary reason for using the framework many years ago).
- TiXL is using C# and the dotnet ecosystem, which has good support on all our target platforms. And over the last years we tried very hard to only use NuGet packages that are cross-platform compatible.
- Slang is a new shader compiler that compiles TiXL's DirectX shader code from HLSL into Vulkan's SPIR-V with very few, non-breaking changes.
- TiXL has very few operators that use DirectX-specific types directly. Most of these building blocks are wrapped away.
- Over the years we have built and maintained a set of visual reference tests: Small images rendered once and used to test feature compatibility and avoid regressions.

Where we're standing now:

TiXL is running extremely well on Linux and macOS. Normal startup time is 1-2s (compared to 10-20s on Windows). Framerates are more stable and Vulkan rendering performance is on the same level. 

All your projects should work. But if you've written custom shader code, there are [a few modifications you might have to make](https://github.com/tixl3d/tixl/blob/feat/linux-port/.help/docs/advanced/UpgradingToVulkan.md).


## Improved UI Scaling

Testing on all three platforms allowed us to improve a lot of layout details related to UI scaling. With Wayland and macOS we can't rely on 96 dpi anymore. So a lot of time went into tweaking font resizing, handling multi-display setups with varying DPIs, adjusting scaling on the fly, etc.

## Trackpad Support

Trackpad support on Windows is extremely limited because most notebook manufacturers use mouse simulation instead of providing access to the touch events. With macOS and Linux this situation improved significantly, so we now have proper pinch zoom and flicking, and all the other fancy things you expect from a nice trackpad.

## Better Framerate Support

We also spent a lot of time supporting different refresh rates. This became more urgent with setups that use multiple displays (e.g. 240 Hz on a MacBook display with an external projector running at 60 Hz). In many areas TiXL was relying on 60 Hz for smoothing animations. We now infer the refresh rate of the primary display the editor is running on.

## MIDI Device Aliases

MIDI device names change with every unit, operating system and USB port, and every `[MidiInput]` that stored one broke with it. Projects can now store an alias such as `TiXL:ApcMini` instead. Which physical device it means is set per machine in Settings » Midi, where existing device-specific names can be replaced with an alias in one step. Teaching stores the alias, and the mapping ships as `midiAliases.json` next to an exported Player, where it can be edited on site. See [MIDI device aliases](../docs/using/MidiDeviceAliases.md).
